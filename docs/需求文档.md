## 1. 项目概述

### 1.1 背景

建筑施工领域"危险性较大的分部分项工程"（以下简称**危大工程**）的合规审查目前高度依赖人工：施工单位编制专项施工方案 → 施工单位技术负责人审核 → 总监理工程师审查 → 超规模工程还需组织 5 名以上专家论证。整个流程存在三大痛点：

1. **法规检索难**：危大工程涉及住建部令第 37 号、建办质〔2018〕31 号、各省市实施细则、几十本 JGJ/GB 行业规范，人工逐条比对耗时长、易遗漏。
2. **审查标准不统一**：不同审查人员对同一条款的把握尺度不一，审查质量依赖个人经验。
3. **知识更新滞后**：新法规、新规范发布后，一线审查人员难以及时全面掌握。

### 1.2 项目目标

构建一个基于 **RAG（检索增强生成）+ 多智能体（Multi-Agent）** 的危大工程合规审查系统，实现：

- 上传专项施工方案（PDF/Word）后，自动解析、自动识别是否属于危大工程、是否超过一定规模。
- 基于法规知识库进行 RAG 检索，由多个专业 Agent 协同完成逐条合规审查，输出带法规条文引用的审查意见。
- 对超过一定规模的危大工程，自动生成专家论证要点清单。
- 生成可导出的合规审查报告（Word/PDF）。
- 提供法规知识库的可视化管理与增量更新能力。
- 提供基于 RAG 的法规智能问答助手。

### 1.3 项目范围

**包含**：
- 后端 API 服务（FastAPI）
- 多智能体编排引擎（LangGraph）
- RAG 检索引擎（向量库 + 混合检索）
- 法规知识库管理（上传、解析、向量化、版本管理）
- 前端 Web 应用（Vue 3 + Element Plus）
- 异步任务处理（文档解析、知识库构建、报告生成）
- 用户与权限管理（RBAC）

**不包含**：
- 移动端 APP
- 与住建部门政务系统的对接（预留接口）
- BIM 模型解析（仅处理 PDF/Word 文本类方案文档）

### 1.4 目标用户

| 角色 | 说明 | 核心功能 |
|------|------|----------|
| 施工单位技术员 | 编制方案后自查 | 上传方案、获取审查意见、修改指引 |
| 总监理工程师 | 方案审查 | 审查工作台、出具审查意见 |
| 安全监督人员 | 政府/企业安监 | 批量审查、统计分析、知识库维护 |
| 系统管理员 | 平台运维 | 用户管理、知识库管理、系统配置 |

## 3. 系统总体架构

### 3.1 分层架构

系统采用**前后端分离 + 分层架构**，后端自下而上分为：

```
┌─────────────────────────────────────────────────────────┐
│                    前端层 (Vue 3 SPA)                     │
│  项目管理 │ 审查工作台 │ 知识库管理 │ 智能问答 │ 仪表盘    │
└──────────────────────────┬──────────────────────────────┘
                           │ HTTPS / RESTful / WebSocket
┌──────────────────────────▼──────────────────────────────┐
│                    API 网关层 (FastAPI)                    │
│  路由 │ 认证鉴权 │ 请求校验 │ 异常处理 │ 限流 │ CORS      │
├──────────────────────────────────────────────────────────┤
│                    业务服务层 (Services)                   │
│  项目服务 │ 文档服务 │ 审查服务 │ 报告服务 │ 知识库服务    │
├──────────────────────────────────────────────────────────┤
│                 多智能体编排层 (LangGraph)                 │
│  Orchestrator │ 7 个专业 Agent │ 共享状态 │ 条件路由       │
├──────────────────────────────────────────────────────────┤
│                    RAG 引擎层                              │
│  文档加载 │ 分块 │ Embedding │ 向量库 │ 混合检索 │ Rerank │
├──────────────────────────────────────────────────────────┤
│                    数据持久层                              │
│  PostgreSQL(业务) │ Redis(缓存/队列) │ 向量库(法规) │ 文件存储 │
└──────────────────────────────────────────────────────────┘
```

### 3.2 核心业务流程（端到端）

```
用户上传专项施工方案
       │
       ▼
[1] 文档解析 Agent ──→ 提取工程概况、分部分项、参数、工艺流程、计算书摘要
       │
       ▼
[2] 危大工程识别 Agent ──→ 匹配七大类范围 + 阈值规则 → 判定"是/否危大"、"是否超规模"
       │
       ▼
[3] 法规检索 Agent ──→ 基于识别结果 + 方案内容 → RAG 检索相关法规条文、规范条款
       │
       ▼
[4] 合规审查 Agent ──→ 逐条对照法规 → 生成"符合/不符合/待确认"审查意见 + 条文引用
       │
       ├── 若超规模 ──→ [5] 专家论证 Agent ──→ 生成论证要点清单 + 风险提示
       │
       ▼
[6] 报告生成 Agent ──→ 汇总全部结果 → 生成结构化审查报告 → 导出 Word/PDF
```

### 3.3 异步任务流程

文档解析、知识库构建、报告导出为耗时操作，通过 Celery 异步执行：

- 前端上传 → API 创建任务 → 返回 `task_id` → 前端轮询 `/api/v1/tasks/{task_id}` 或通过 WebSocket 接收进度。
- 任务状态：`PENDING` → `RUNNING` → `SUCCESS` / `FAILURE`，进度百分比实时更新。

### 4.4 核心业务服务逻辑

#### 4.4.1 文档解析服务（`document_service.py`）

**解析流程**：
1. 校验文件类型（pdf/docx/doc/txt）与大小（≤100MB）。
2. 保存到 `UPLOAD_DIR/{project_id}/{document_id}_{filename}`。
3. 创建 `documents` 记录，`parse_status=pending`。
4. 提交 Celery 任务 `parse_document_task(document_id)`。
5. Celery 任务内：
   - PDF：PyMuPDF 逐页提取文本，保留页码；尝试提取表格（`page.find_tables()`）。
   - DOCX：python-docx 提取段落、表格、标题样式（heading level）。
   - 合并为带标题层级的结构化文本，记录 `heading_path`。
   - 统计页数、字数。
   - 更新 `parsed_content`（前 5000 字符预览）、`page_count`、`word_count`、`parse_status=parsed`。
   - 若为知识库文档（`doc_category=regulation`），不自动分块，等待用户触发知识库构建。

#### 4.4.2 审查服务（`review_service.py`）

**创建审查流程**：
1. 校验项目与文档存在，且文档已 `parsed`。
2. 创建 `reviews` 记录，`status=pending`。
3. 调用 `orchestrator.run_review(review_id)`（内部提交 Celery 任务，避免阻塞 API）。
4. Celery 任务内执行 LangGraph 工作流（详见第 6 章），逐步更新 `reviews` 各字段与 `review_items`。
5. 工作流完成后更新 `status=completed`、`completed_at`。

**人工确认流程**：
- 用户可对某条 `review_items` 的 `compliance_status` 进行修正，并填写 `human_note`（需在 review_items 表增加 `human_note` 字段，类型 TEXT，可空）。
- 修正后该条意见标记 `human_confirmed=true`（增加字段 BOOLEAN DEFAULT false）。
- 重新生成报告时以人工确认后的状态为准。

> 注：请在 `review_items` 表中补充 `human_note TEXT` 和 `human_confirmed BOOLEAN DEFAULT false` 两个字段。

## 5. RAG 引擎与知识库设计

### 5.1 RAG 整体流水线

```
法规文档(PDF/Word)
    │
    ▼
[文档加载器 Loader] ──→ 纯文本 + 元数据(标题/页码/法规名)
    │
    ▼
[语义分块器 Splitter] ──→ 按标题层级 + 字符数(512 tokens, overlap 64)分块
    │
    ▼
[Embedding 模型] ──→ 每块生成 1024/1536 维向量
    │
    ▼
[向量库 VectorStore] ──→ 持久化存储，元数据(category/regulation_name/clause_number)
    │
    ▼
[混合检索 Retriever] ──→ 向量相似度 + BM25 关键词 + 元数据过滤 → 候选集 Top 20
    │
    ▼
[重排序 Reranker] ──→ BGE-Reranker / Cohere → Top 5
    │
    ▼
[Prompt 组装] ──→ 上下文(法规条文) + 用户问题 → LLM 生成回答
```

### 5.2 文档加载器（`loader.py`）

**接口定义**：
```python
class BaseLoader(ABC):
    @abstractmethod
    def load(self, file_path: str) -> list[DocumentSegment]:
        ...

@dataclass
class DocumentSegment:
    content: str
    page_number: int | None
    heading_path: str | None
    metadata: dict
```

**实现**：
- `PDFLoader`：PyMuPDF，按页提取；检测标题（字体大小突变/加粗）构建 heading_path；表格转为 Markdown 表格文本。
- `DOCXLoader`：python-docx，遍历 paragraphs，利用 `style.name` 判断 heading level；tables 转为 Markdown。
- `TXTLoader`：按空行分段，无 heading。
- `LoaderFactory`：根据文件后缀返回对应 Loader。

### 5.3 语义分块器（`splitter.py`）

**策略**：基于标题层级的递归分块（Hierarchical Splitter）。
1. 先按一级标题切分。
2. 若某节超过 `chunk_size`（默认 512 tokens），按二级标题切分。
3. 仍超长则按段落切分。
4. 最后按字符数（`RecursiveCharacterTextSplitter`）兜底。
5. 相邻块保留 `chunk_overlap`（默认 64 tokens）。
6. 每个块记录 `heading_path`（如 "二、模板工程及支撑体系 > （一）工具式模板工程"）。

**参数可配置**：`chunk_size`、`chunk_overlap` 通过知识库构建 API 传入。

> **v2.0 选型说明**：移除 Milvus 实现，改为 PGVector + Chroma 双实现。
> 理由：① PG 扩展零额外容器成本；② 与业务数据同库，便于事务与关联查询；
> ③ 本机磁盘余量有限，Milvus 独立部署的镜像与运维开销不划算。

**元数据过滤**：支持按 `category`、`entry_type`、`regulation_name`、`is_active` 过滤。

### 5.6 混合检索器（`retriever.py`）

**检索策略**：
1. **向量检索**：query embedding → 向量库 Top 20。
2. **BM25 检索**：对 `knowledge_chunks.content` 建 BM25 索引（使用 `rank_bm25` 库，索引存 Redis 或内存），关键词检索 Top 20。
3. **合并去重**：按 `chunk_id` 合并，向量相似度与 BM25 分数归一化后加权求和（默认向量 0.6 + BM25 0.4）。
4. **元数据过滤**：在检索前或检索后按 category 等过滤。
5. **Rerank**：Top 20 → Reranker → Top 5（若未配置 Reranker 则直接取 Top 8）。

**检索接口**：
```python
def retrieve(self, query: str, top_k: int = 5,
             category: str | None = None,
             entry_type: str | None = None) -> list[RetrievedChunk]:
    ...
```

### 5.7 知识库构建与更新

#### 5.7.1 构建流程（`knowledge_tasks.py`）

1. 用户上传法规文档（`doc_category=regulation`）。
2. 文档解析完成后，用户在知识库管理页点击"构建知识库"或通过 API `POST /knowledge/build`。
3. 创建 `knowledge_build_tasks` 记录，提交 Celery 任务。
4. Celery 任务内：
   a. 调用 Loader 加载文档 → `DocumentSegment` 列表。
   b. 调用 Splitter 分块 → `Chunk` 列表（含 heading_path、page_number）。
   c. 对每个法规文档，创建一条或多条 `knowledge_entries`（按一级标题拆分为条目，或整个文档为一个条目）。
   d. 创建 `knowledge_chunks` 记录，关联 entry。
   e. 批量调用 Embedding（每批 32 条）生成向量。
   f. 批量写入向量库，metadata 含 `knowledge_chunk_id`、`entry_id`、`category`、`regulation_name`、`clause_number`、`is_active`。
   g. 更新任务进度 `processed_chunks / total_chunks`。
   h. 完成后 `status=completed`。

#### 5.7.2 更新策略

- **增量更新**：上传新法规文档 → 独立构建，不影响已有向量。
- **版本更新**：同一法规修订后，上传新版 → 创建新版本条目（`version` 递增），旧版本 `is_active=false`，向量库中旧版本 chunk 的 metadata `is_active=false`（检索时默认过滤 `is_active=true`）。
- **删除**：删除 entry → 级联删除 chunks + 向量库中对应向量（按 `entry_id` 元数据过滤删除）。
- **全量重建**：`POST /knowledge/reindex` → 清空向量库 → 遍历所有 `is_active=true` 的 entry 的 chunks 重新 embedding 写入。用于更换 embedding 模型或向量库后。

### 5.8 RAG 问答流水线（`pipeline.py`）

```python
class RAGPipeline:
    def __init__(self, retriever, llm, prompt_template):
        ...

    def query(self, question: str, category: str | None = None) -> RAGAnswer:
        # 1. 检索
        chunks = self.retriever.retrieve(question, top_k=5, category=category)
        # 2. 组装上下文
        context = "\n\n".join([
            f"[{i+1}] {c.regulation_name} {c.clause_number}:\n{c.content}"
            for i, c in enumerate(chunks)
        ])
        # 3. 构造 Prompt
        prompt = self.prompt_template.format(question=question, context=context)
        # 4. LLM 生成
        answer = self.llm.invoke(prompt)
        # 5. 返回答案 + 来源
        return RAGAnswer(answer=answer, sources=chunks)
```

## 6. 多智能体（Multi-Agent）系统设计

### 6.1 设计原则

- **单一职责**：每个 Agent 只负责一个明确的专业环节。
- **共享状态**：所有 Agent 通过 LangGraph 的共享 `State` 传递数据，不直接互相调用。
- **编排器控制**：由 Orchestrator（LangGraph 状态图）决定执行顺序与条件分支，Agent 之间不直接通信。
- **可观测**：每个 Agent 的输入、输出、耗时、token 消耗记录到 `agent_trace`。
- **可重试**：LLM 调用失败自动重试 2 次，仍失败则标记该环节失败但不中断整体流程（降级处理）。

```
   - 基坑：开挖深度、支护形式、降水方式、基坑周长/面积

   - 起重吊装：单件起吊重量、起重设备型号、吊装高度、吊装方法
   - 脚手架：搭设高度、脚手架类型（落地式/附着式/悬挑式/吊篮）
   - 拆除爆破：拆除面积/高度、爆破方式、周围环境
   - 暗挖：施工方法（矿山法/盾构/顶管）、断面尺寸、长度
   - 其他：幕墙高度、钢结构跨度、人工挖孔桩深度、水下作业深度
3. 施工工艺流程：主要工序步骤。
4. 安全保证措施：已列出的安全措施类别。
5. 监测方案：监测项目、监测频率、报警值。
6. 应急处置：应急预案要点。
7. 计算书：是否包含计算书，计算项目列表。

输出格式：严格输出 JSON，键名为上述类别，未提及的参数值为 null。
只提取文本中明确出现的信息，不得推测或编造。
```

**实现要点**：
- 若全文过长（> 8000 tokens），按章节分块提取后合并（Map-Reduce 模式）。
- 输出强制 JSON 解析（使用 `llm.with_structured_output(ExtractedParams)` 或 Pydantic 模型）。
- 提取失败时降级：`extracted_params` 留空，记录 error，流程继续。

#### 6.4.2 危大工程识别 Agent（`hazard_identifier_agent.py`）

**职责**：基于提取的参数，对照危大工程范围（七大类）与超过一定规模的阈值，判定是否属于危大工程、属于哪些类别、是否超规模。

**输入**：`extracted_params`、`parsed_text`（前 3000 字作为补充）。

**输出**：`is_hazard_project`、`hazard_categories`、`is_over_scale`、`identification_basis`。

**System Prompt**：
```
你是一名建筑施工安全专家，精通《危险性较大的分部分项工程安全管理规定》（住建部令第37号）及建办质〔2018〕31号文。

请根据以下工程参数，判断该工程是否包含危险性较大的分部分项工程（危大工程），以及是否超过一定规模。

【危大工程范围（七大类）】
一、基坑工程：开挖深度≥3m，或<3m但地质/周边复杂；超规模：开挖深度≥5m。
二、模板工程及支撑体系：工具式模板（滑模/爬模/飞模/挂篮）；混凝土模板支撑搭设高度≥5m或跨度≥10m或施工总荷载≥10kN/㎡或集中线荷载≥15kN/m；承重支撑体系。超规模：搭设高度≥8m或跨度≥18m或施工总荷载≥15kN/㎡或集中线荷载≥20kN/m。
三、起重吊装及安装拆卸：非常规起重且单件起吊重量≥10kN；采用起重机械安装；起重机械安装拆卸。超规模：非常规起重且单件起吊重量≥100kN；起重量≥300kN的起重设备安装工程；高度≥200m内爬起重设备拆除。
四、脚手架工程：落地式钢管脚手架搭设高度≥24m；附着式升降脚手架；悬挑式脚手架；高处作业吊篮；卸料/操作平台；异型脚手架。超规模：落地式脚手架搭设高度≥50m；提升高度≥150m附着式升降脚手架；分段架体搭设高度≥20m悬挑式脚手架。
五、拆除爆破工程：拆除工程；采用爆破拆除。超规模：拆除可能影响毗邻建筑的；采用爆破拆除的。
六、暗挖工程：矿山法/盾构法/顶管法施工的隧道洞室。超规模：全部暗挖工程均超规模。
七、其他：建筑幕墙安装；钢结构/网架/索膜结构安装；人工挖孔桩；水下作业；装配式建筑预制构件安装；四新技术。超规模：施工高度≥50m建筑幕墙；跨度≥36m钢结构安装；开挖深度≥16m人工挖孔桩；水下作业工程。

判断要求：
1. 逐项对照七大类，列出所有命中的类别。
2. 每个命中类别标注：类别编码、类别名称、是否超规模、判定依据（引用具体参数和阈值）。
3. 只要有一个类别命中，is_hazard_project即为true。
4. 只要有一个类别超规模，is_over_scale即为true。
5. 若参数不足无法判断，标注"待确认"并说明缺少什么参数。

输出格式：严格JSON。
```

**实现要点**：
- 此 Agent 同时使用**规则引擎**作为辅助：将阈值规则硬编码为 Python 函数（如 `check_foundation_pit(depth) -> HazardCategory`），先跑规则得到初步结果，再由 LLM 复核与补充（处理复杂语义场景）。规则结果与 LLM 结果不一致时以 LLM 为准但记录差异。
- 规则引擎代码放在 `app/agents/rules/hazard_rules.py`。

#### 6.4.3 法规检索 Agent（`regulation_retrieval_agent.py`）

**职责**：基于识别出的危大类别和方案内容，生成检索查询，调用 RAG 检索相关法规条文。

**输入**：`hazard_categories`、`extracted_params`、`document_structure`。

**输出**：`retrieved_regulations`。

**实现逻辑**（此 Agent 以程序化为主，LLM 辅助生成检索 query）：
1. 对每个命中的 `hazard_category`，生成 2-3 个检索查询：
   - 查询1："{类别名} 危大工程 范围"
   - 查询2："{类别名} 专项施工方案 编制要求"
   - 查询3：基于具体参数的查询，如"开挖深度8m基坑 支护 监测 要求"
2. 调用 `retriever.retrieve(query, category=category_code, top_k=5)`。
3. 合并所有查询结果，去重（按 `regulation_name + clause_number`），按相关度排序取 Top 20。
4. 若某类别检索结果不足 3 条，放宽 category 过滤重新检索。
5. LLM 辅助：对检索到的条文进行相关性二次筛选（"该条文是否与本工程的审查直接相关"），剔除不相关条目。

#### 6.4.4 合规审查 Agent（`compliance_reviewer_agent.py`）

**职责**：核心审查环节。对照检索到的法规条文，逐条审查专项施工方案的合规性，生成审查意见。

**输入**：`parsed_text`、`extracted_params`、`retrieved_regulations`、`hazard_categories`。

**输出**：`review_items`。

**审查维度（8 大类，对应 `review_items.category`）**：

| 维度编码 | 维度名称 | 审查要点 |
|----------|----------|----------|
| completeness | 方案完整性 | 方案是否包含工程概况、编制依据、施工计划、施工工艺、安全保证措施、验收要求、应急处置、计算书及图纸等 9 项必备内容（37号令第十一条） |
| procedure | 审批程序 | 是否经施工单位技术负责人审核签字盖章、总监理工程师审查签字盖章；分包编制的是否经总包和分包共同审核 |
| technical_params | 技术参数 | 施工工艺流程、技术参数是否满足设计工况和规范要求 |
| calculation | 计算书 | 计算书和验算依据、施工图是否符合标准规范；荷载取值、计算模型是否正确 |
| safety_measure | 安全措施 | 安全保证措施是否有针对性和可操作性；安全技术交底、安全教育、防护设施 |
| monitoring | 监测方案 | 监测项目、监测频率、报警值是否合理；监测数据反馈机制 |
| acceptance | 验收要求 | 验收标准、程序、内容、人员是否符合规定 |
| emergency | 应急处置 | 应急处置措施是否有针对性和有效性；应急预案、应急物资、应急演练 |

**System Prompt**：
```
你是一名资深建筑施工安全合规审查专家，正在对一份专项施工方案进行合规审查。

【工程信息】
{工程概况与提取的参数}

【命中的危大工程类别】
{hazard_categories}

【相关法规条文】
{retrieved_regulations，逐条列出法规名、条款号、原文}

【方案全文】
{parsed_text，若过长则按审查维度分段提供}

审查任务：
请从以下 8 个维度逐条审查方案的合规性：
1. completeness 方案完整性
2. procedure 审批程序
3. technical_params 技术参数
4. calculation 计算书
5. safety_measure 安全措施
6. monitoring 监测方案
7. acceptance 验收要求
8. emergency 应急处置

对每个维度，生成 1-5 条具体审查意见。每条意见包含：
- item_title: 审查项标题（简洁概括）
- category: 维度编码
- scheme_content: 方案中对应内容的原文摘录（若方案未提及则填"方案未提及"）
- regulation_reference: 引用的法规条文（格式："《法规名》第X条：条文原文"）
- compliance_status: compliant（符合）/ non_compliant（不符合）/ needs_confirmation（待确认）/ not_applicable（不适用）
- severity: critical（严重，必须整改）/ major（主要，应当整改）/ minor（一般，建议整改）/ suggestion（建议优化）
- review_comment: 审查意见详情（说明为什么符合/不符合，具体问题在哪）
- modification_suggestion: 修改建议（若不符合或待确认，给出具体修改方向；符合则填null）

审查原则：
1. 严格依据提供的法规条文，不得引用未提供的法规。
2. 方案未提及某项要求时，判定为 non_compliant 或 needs_confirmation（若该要求为强制性条文则 non_compliant）。
3. 区分"强制性条文"（必须执行）与"推荐性条文"（建议执行），强制性条文不符合时 severity 至少为 major。
4. 意见要具体、可操作，避免泛泛而谈。
5. 若方案内容明显优于法规要求，判定为 compliant 并可在 comment 中说明。

输出格式：严格输出 JSON 数组，每个元素为一条审查意见。
```

**实现要点**：
- 由于方案全文可能很长，采用**分段审查 + 汇总**策略：
  - 对每个审查维度，从方案中提取相关章节（基于 `document_structure` 的 heading_path 匹配），作为该维度的上下文。
  - 每个维度单独调用一次 LLM，生成该维度的审查意见。
  - 8 个维度可并行调用（使用 `asyncio.gather`）。
  - 最后汇总所有维度的意见，按 severity 降序排序。
- 每次 LLM 调用强制 JSON 输出，解析失败重试 2 次，仍失败则该维度生成一条 `needs_confirmation` 的兜底意见。
- 审查意见写入 `review_items` 表，`agent_source='compliance_reviewer'`。

#### 6.4.5 专家论证 Agent（`expert_argumentation_agent.py`）

**职责**：仅对超过一定规模的危大工程执行。模拟专家论证会视角，生成专家论证要点清单与风险提示。

**输入**：`hazard_categories`（超规模类别）、`extracted_params`、`review_items`（已发现的问题）、`retrieved_regulations`。

**输出**：`expert_points`。

**System Prompt**：
```

请基于工程信息和初步审查结果，生成专家论证要点清单。每个要点应包含：
- point_title: 论证要点标题
- point_content: 详细说明专家应重点关注、论证的内容，以及方案中可能存在的风险
- risk_level: high（高风险，必须论证清楚）/ medium（中风险，应当关注）/ low（低风险，建议关注）

输出格式：严格输出 JSON 数组。
```

**实现要点**：
- 仅在 `is_over_scale=true` 时执行（由条件路由控制）。

#### 6.4.6 报告生成 Agent（`report_generator_agent.py`）

**职责**：汇总所有 Agent 的输出，生成结构化的审查报告内容，计算综合评分与结论。

**输入**：完整的 `ReviewState`。

**输出**：`report_outline`、`overall_score`、`overall_conclusion`。

**报告结构（`report_outline`）**：
```json
{
  "report_title": "XX专项施工方案合规审查报告",
  "report_number": "HG-2026-0001",
  "sections": [
    {
      "heading": "一、工程概况",
      "content": "..."
    },
    {
      "heading": "二、审查依据",
      "content": "列出引用的所有法规名称"
    },
    {
      "heading": "三、危大工程识别结果",
      "content": "命中类别、是否超规模、识别依据"
    },
    {
      "heading": "四、合规审查意见",
      "content": "按8个维度分组的审查意见表格（含状态、严重程度、意见、修改建议、法规引用）"
    },
    {
      "heading": "五、专家论证要点（如适用）",
      "content": "专家论证要点清单"
    },
    {
      "heading": "六、综合评价与结论",
      "content": "综合评分、结论（通过/修改后通过/不通过）、主要问题汇总、整改建议"
    },
    {
      "heading": "七、声明",
      "content": "本报告由AI系统辅助生成，仅供参考，最终审查结论以具有相应资质的专业人员签字为准。"
    }
  ]
}
```

**综合评分算法**：
- 初始分 100。
- 每条 `non_compliant` 意见扣分：`critical` -15，`major` -8，`minor` -3，`suggestion` -1。
- 每条 `needs_confirmation` 意见扣分：`critical` -8，`major` -4，`minor` -1。
- 最低 0 分。
- 结论判定：
  - `score >= 85` 且无 `critical` 非合规 → `pass`（通过）
  - `60 <= score < 85` 或有 `major` 非合规但无 `critical` → `pass_with_modification`（修改后通过）
  - `score < 60` 或有 `critical` 非合规 → `fail`（不通过）

**实现要点**：
- 报告内容以结构化 JSON 存入 `reports.content_json`。
- 报告编号规则：`HG-{年份}-{4位序号}`，序号从数据库查询当年最大序号 +1。
- 此 Agent 以程序化生成为主（模板填充），LLM 仅用于"综合评价"段落的自然语言润色。

### 6.5 编排器（`orchestrator.py`）

```python
class ReviewOrchestrator:
    def __init__(self, db_session, rag_pipeline, llm):
        self.graph = build_review_graph(llm, rag_pipeline, db_session)
        self.db = db_session

    async def run_review(self, review_id: str) -> None:
        # 1. 从数据库加载 review、document、project 信息
        review = await get_review(self.db, review_id)
        document = await get_document(self.db, review.document_id)
        # 2. 初始化 state
        state = ReviewState(
            review_id=str(review.id),
            project_id=str(review.project_id),
            document_id=str(review.document_id),
            document_title=document.title,
            parsed_text=document.parsed_content or "",  # 若预览不全则从文件读取全文
            document_structure=[],
            extracted_params={},
            is_hazard_project=False,
            hazard_categories=[],
            is_over_scale=False,
            identification_basis="",
            retrieved_regulations=[],
            review_items=[],
            expert_points=[],
            report_outline={},
            overall_score=0,
            overall_conclusion="",
            current_step="init",
            agent_trace=[],
            errors=[]
        )
        # 3. 更新 review status=running
        await update_review_status(self.db, review_id, "running")
        # 4. 执行 LangGraph（异步流式，每步更新数据库）
        try:
            async for event in self.graph.astream(state, stream_mode="updates"):
                # 每个 node 执行完后，把关键结果持久化到数据库
                await self._persist_step(event, review_id)
        except Exception as e:
            state["errors"].append(str(e))
            await update_review_status(self.db, review_id, "failed", error=str(e))
            return
        # 5. 最终状态持久化
        final_state = self._get_final_state()  # 从 graph 结果中取
        await self._persist_final(final_state, review_id)
        await update_review_status(self.db, review_id, "completed")

    async def _persist_step(self, event, review_id):
        # 根据 node 名，把对应结果写入数据库
        # 例如 "identify" 节点完成后更新 reviews.is_hazard_project 等
        # "review" 节点完成后批量写入 review_items
        ...
```

### 6.6 Agent 之间的协调机制总结

| 协调方式 | 说明 |
|----------|------|
| 共享状态 | 所有 Agent 读写同一个 `ReviewState`，前一个 Agent 的输出是后一个的输入 |
| 条件路由 | LangGraph 的 `add_conditional_edges` 根据 state 中的字段（`is_hazard_project`、`is_over_scale`）决定走哪条分支 |
| 顺序执行 | 解析 → 识别 → 检索 → 审查 →（专家论证）→ 报告，严格按依赖顺序 |
| 并行执行 | 合规审查 Agent 内部 8 个维度并行调用 LLM；法规检索 Agent 内部多 query 并行检索 |
| 降级容错 | 单个 Agent 失败不中断整体流程，记录 error 后用兜底结果继续 |
| 持久化同步 | 每步执行完立即把结果写入数据库，即使后续步骤失败，已完成的结果仍可查看 |

#### 7.4.8 审查工作台（`ReviewWorkbenchView.vue`）—— 核心页面

**布局：三栏式**

```
┌──────────────────────────────────────────────────────────┐
│  审查名称 | 状态:运行中 | 进度:审查中 | [刷新] [生成报告]  │
├──────────────┬───────────────────────┬───────────────────┤
│              │                       │                   │
│  左栏(280px) │   中栏(弹性)           │   右栏(360px)     │
│              │                       │                   │
│  Agent流程   │   审查意见列表          │   方案原文          │
│  进度面板    │   (按维度分组)          │   (可滚动)          │
│              │                       │                   │
│  - 文档解析  │   [维度Tab]            │   顶部:章节搜索     │
│    ✓ 完成    │   完整性 程序 技术...   │   内容:带高亮       │
│  - 危大识别  │                       │                   │
│    ✓ 完成    │   意见卡片:             │                   │
│  - 法规检索  │   标题 + 状态标签       │                   │
│    ✓ 完成    │   方案摘录              │                   │
│  - 合规审查  │   法规引用(可展开)      │                   │
│    ⏳ 进行中  │   审查意见              │                   │
│  - 专家论证  │   修改建议              │                   │
│    ○ 待执行  │   [确认] [修改状态]     │                   │
│  - 报告生成  │                       │  点击意见中的"方案  │
│    ○ 待执行  │                       │  摘录"自动滚动定位  │
│              │                       │  到原文对应位置     │
└──────────────┴───────────────────────┴───────────────────┘
```

**左栏 - Agent 流程进度**：
- 垂直步骤条，显示 6 个 Agent 节点的状态（已完成✓绿色、进行中⏳蓝色动画、待执行○灰色、失败✗红色）。
- 进行中的节点下方显示子进度（如"合规审查：5/8 维度完成"）。
- 每 3 秒自动轮询刷新状态（`useTaskPolling`）。

**中栏 - 审查意见**：
- 顶部：维度 Tab（全部 / 完整性 / 审批程序 / 技术参数 / 计算书 / 安全措施 / 监测方案 / 验收要求 / 应急处置），每个 Tab 右上角显示该维度的意见数和非合规数（红色角标）。
- 筛选：状态筛选（全部/不符合/待确认/符合）、严重程度筛选。
- 意见卡片（`ReviewItemCard`）：
  - 标题行：`item_title` + 状态标签（符合绿色/不符合红色/待确认橙色/不适用灰色）+ 严重程度标签。
  - 方案摘录：灰色引用块，点击可在右栏定位。
  - 法规引用：可折叠，展开显示法规名、条款号、条文原文。
  - 审查意见：正文。
  - 修改建议：蓝色提示框（若有）。
  - 操作栏："确认此意见"按钮、"修改状态"下拉（人工修正）、添加备注输入框。
- 意见按严重程度排序（critical → major → minor → suggestion）。

**右栏 - 方案原文**：
- 顶部：搜索框（在原文中搜索关键词）、字体大小调节。
- 内容：方案全文，按段落渲染，页码标注在右侧。
- 当点击中栏意见的"方案摘录"时，右栏自动滚动到对应位置并高亮（黄色背景）。
- 支持用户手动选中文本后右键"标记为问题"（可选功能，v1.5）。

**底部状态栏**：
- 显示当前审查的总体信息：命中类别、超规模、已生成意见数、非合规数、预计完成时间。
- "生成审查报告"按钮（审查完成后可用）。

```typescript
import axios from 'axios'

// 请求拦截：附 token
request.interceptors.request.use(config => {

  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

// 响应拦截：统一处理 code !== 0

  response => {

    }
    return res.data  // 直接返回 data 字段
  },
  error => {
    ElMessage.error(error.message || '网络错误')
    return Promise.reject(error)
  }
)

export default request
```

## 9. 评测体系 Eval 与 Benchmark

> **JD 频次：34%** —— 100 份 JD 中 34 份明确要求评测能力，
> **高于向量数据库(21%)、Docker(13%)、FastAPI(9%)**，是本项目最大的单项缺口。
>
> 典型 JD 原文：
> - 腾讯：「构建**可量化的 Agent 效果评估体系**，建立"评测→反馈→调优→再评测"的持续迭代闭环」
> - 某半导体岗：「构建评测数据集（**Golden Dataset**）、设计评测指标
>   （**Faithfulness、Answer Relevancy、Context Precision**），实现自动化评测流水线」
> - 小红书：「建设**离线评测集、过程评测、端到端评测、Bad Case 归因**和线上指标监控」
> - 金蝶：「搭建 Agent 的**观测体系与全链路追踪，建立自动化评测与回测机制**」
>
> **本项目已有基础**：`rag/evidence.py` 的拒答机制已实现「无依据不输出」，
> 需将其纳入评测指标体系。

### 9.1 评测集设计（`eval/`）

分三层，覆盖不同验证目标：

| 评测集 | 规模 | 数据来源 | 验证目标 | 构建方式 |
|---|---|---|---|---|
| **回归集** | 100 条 | 住建部 37 号令 + 建办质 31 号文 + JGJ 规范原文 | 改代码后确认没退化 | 固定不变，每次 CI 全跑 |
| **标注集** | 700 条 | 同上，人工标注标准答案与法条引用 | 量化检索质量 | 分层抽样，覆盖 7 大类 |
| **对抗集** | 50 条 | 故意构造的问题 | 验证拒答机制 | 含超纲问题、歧义问题、诱导性问题 |

**必须按危大工程七大类分层**，否则指标会被高频类别主导：

```
foundation_pit基坑工程          ≥ 15%
formwork          模板工程        ≥ 15%
lifting           起重吊装        ≥ 12%
scaffold          脚手架工程        ≥ 12%
demolition        拆除爆破        ≥ 12%
underground暗挖工程        ≥ 12%
other             其他            ≥ 12%
```

**评测集数据格式**（JSONL）：

```json
{
  "case_id": "fp_001",
  "question": "模板支撑立杆的纵横向间距最大不超过多少？",
  "category": "formwork",
  "expect_answer": "不应大于900mm",
  "expect_clauses": ["JGJ 80-2016 第4.2.1条"],
  "expect_risk": "high",
  "difficulty": "direct",
  "note": "教材级基础题，考察精确条款号召回"
}
```

`difficulty` 分四档：`direct`（直给条款）/ `semantic`（口语化同义问）/ `cross_ref`（跨条款综合）/ `adversarial`（应拒答）。

### 9.2 指标定义（`eval/metrics.py`）

**检索层指标**：

| 指标 | 定义 | 目标 |
|---|---|---|
| Recall@5 | Top-5 召回的期望条款数 / 期望条款总数 | ≥ 95% |
| MRR | 期望条款首次出现排名的倒数均值 | ≥ 0.9 |
| 命中率 | Top-5 中存在任一期望条款的查询比例 | ≥ 98% |

**生成层指标**：

| 指标 | 定义 | 目标 |
|---|---|---|
| **Faithfulness** | 结论中每个断言是否都能在检索到的原文里找到支撑 | ≥ 95% |
| **Answer Relevancy** | 回答是否切题 | ≥ 90% |
| **Context Precision** | 检索到的 Top-K 中相关条文的占比 | ≥ 80% |
| **Citation Accuracy** | 引用格式正确率（规范号+条号+原文） | 100% |
| **拒答准确率** | 对抗集中应拒答的实际拒答比例 | ≥ 95% |
| **误拒率** | 正常问题被错误拒答的比例 | ≤ 3% |

**系统级指标**：

| 指标 | 目标 |
|---|---|
| 端到端任务完成率 | ≥ 90% |
| 单次审查总 token 消耗 | 见第 12 章 |
| P95 端到端延迟 | ≤ 5 分钟 |

### 9.3 自动化评测流水线（`eval/runner.py`）

```
pytest test_eval/ -m eval          # 一键跑全量评测
     ↓
加载评测集 → 走完整RAG+Agent 链路 → 收集结果
     ↓
计算各项指标 → 输出报告（JSON + Markdown）
     ↓
与基线对比 → 回归检测（有指标下降超阈值则标记失败）
```

**实现要求**：
- 评测必须走**真实链路**（真实检索 + 真实 LLM 调用），不能 mock 检索结果
- LLM 调用需支持 mock 模式，避免跑一次评测烧几十元
- 输出 `eval/reports/baseline.json`，作为回归基线
- 提供 `--compare` 参数，输出与基线的差异表

### 9.4 Bad Case 归因

每次评测自动产出 `bad_cases.jsonl`，按失败原因分类：

| 失败类型 | 归因方向 |
|---|---|
| `recall_miss` | 检索没召回 → 调整分块策略 / 加 BM25 权重 |
| `rerank_miss` | 召回了但没排进 Top-5 → 调 Reranker |
| `refuse_over` | 应答却拒答 → 降阈值 |
| `refuse_under` | 应拒却答了 → 升阈值 / 补对抗样本 |
| `hallucination` | 引用与原文不符 → 检查 evidence 校验 |
| `wrong_clause` | 引用了错误条款 → 检查条号绑定 |

**这是面试可讲的工程闭环**：不是「我做了个 RAG」，而是「我建了评测集，
发现某类问题，做了 X 优化，指标从 A 提到 B」。

### 9.5 CI 集成

GitHub Actions 中每次 PR 运行回归集（100 条），
任一核心指标下降 > 3% 则 CI 失败。

### 10.1 Token 预算管理（`agents/context.py`）

**核心约束**：单次审查总 token 消耗必须可控，不能因为多轮对话无限膨胀。

```python
@dataclass
class TokenBudget:
    """全局预算，按环节分配，超额即降级而非报错。"""
    total: int = 100_000# 单次审查总预算
    by_stage: dict[str, int] = field(default_factory=lambda: {
        "document_parse": 15_000,
        "hazard_identify": 5_000,
        "regulation_retrieval": 10_000,
        "compliance_review": 40_000,
        "expert_argumentation": 20_000,
        "report_generate": 10_000,
    })

    def remaining(self, stage: str) -> int: ...
    def is_exhausted(self, stage: str) -> bool: ...
```

**超预算降级策略**（按序触发，不中断流程）：

1. 降低 RAG 召回数量（20 → 10 → 5）
2. 压缩历史对话（见 10.3）
3. 启用模型降级（DeepSeek → 本地小模型）
4. 标记该环节为「降级执行」，写入 trace

### 10.2 检索结果的组织与回填

不是把 Top-K 原文直接拼进 prompt——那会浪费大量 token 且稀释重点。

```
检索结果 → 去重合并 → 按条款号聚类 → 按相关性压缩为要点
        → 保留最强 2 条原文 + 其余仅保留「规范号+条号+摘要」
```

**实现要求**：
- 保留原文的条款必须能一键展开查看（前端交互）
- 每条注入内容标注来源，便于模型引用溯源
- 压缩率作为指标记录（见第 12 章）

### 10.3 上下文压缩（`agents/compression.py`）

| 策略 | 触发条件 | 方法 |
|---|---|---|
| 历史摘要压缩 | 对话轮次 > 10 | 滚动摘要：保留最近 3 轮原文，更早的压缩为摘要 |
| 工具输出裁剪 | 单次工具输出 > 2000 token | 取头部 + 尾部，标注「中间已省略」 |
| 重复内容去重 | 检索结果间相似度 > 0.9 | 合并同类条款 |
| 引用合并 | 同一条文多次出现 | 只保留一次，合并引用次数 |

### 10.4 短期记忆与长期记忆

**短期记忆**（会话内）：
- `ChatSession` / `ChatMessage` 表已定义（第 4.2.13/4.2.14 节）
- 实现消息历史窗口 + 滚动摘要

**长期记忆**（跨会话）：
- 用户偏好（常用危大类别、常用检索策略）
- 历史审查任务（同类方案再次审查时复用结论）
- 存 PostgreSQL（结构化偏好）+ 向量库（语义相似历史）

**记忆召回策略**：
```
长期记忆检索 → 与当前问题相似度 > 0.7 才注入
              → 最多注入 3 条，避免上下文污染
```

### 10.5 状态隔离（`agents/state.py`）

多用户并发时，上下文必须严格隔离：

- 会话级 `State` 只在单次请求内传递，不共享
- LangGraph 状态图使用 `thread_id`（RunnableConfig）隔离 checkpoint
- 用户 A 的检索结果绝不能出现在用户 B 的上下文中

## 11. MCP 工具服务器

> **JD 频次：20%**（校招 17% / 社招 29%）—— 涨势最强的新兴要求。
> 部分 JD 已把 MCP 与 Tool Calling 并列考察。

### 11.1 为什么用 MCP（不只是能用，而是要讲得清）

MCP（Model Context Protocol）的价值是**工具与Agent 解耦**：
Agent 不需要知道规范检索是查 Milvus 还是 PGVector，只需要知道「有个工具能按条款号查规范」。

面试要能答出这三点：
1. **解决了什么问题** —— 工具复用（多个 Agent 共享同一套工具）、解耦、跨客户端
2. **本项目怎么用** —— 6 个 Agent 共享 5 个 MCP 工具
3. **边界在哪** —— 本地 stdio 部署，不涉及远程 MCP 的鉴权与沙箱问题

### 11.2 工具清单（`mcp/servers/regulation_server.py`）

| 工具 | 功能 | 被哪些 Agent 调用 |
|---|---|---|
| `search_regulation` | 按关键词/条款号/类别检索法规条文 | RegulationRetrieval、ComplianceReviewer |
| `get_clause_detail` | 按规范号+条号取完整原文 | ComplianceReviewer、ReportGenerator |
| `check_version_validity` | 校验规范是否现行有效（是否废止） | ComplianceReviewer |
| `parse_document` | 解析上传的方案文档，返回结构化内容 | DocumentParser |
| `export_report` | 导出审查报告 Word/PDF | ReportGenerator |
| `list_hazard_categories` | 返回七大类及其判定阈值 | HazardIdentifier |

- 使用 **FastMCP**（Python MCP SDK）实现，stdio 传输

- 工具实现类内部复用现有 RAG 检索层，不重复实现检索逻辑
- 提供工具自测脚本 `mcp/test_tools.py`，可脱离 LLM 验证每个工具行为

```python
    审查危大工程专项方案时，用于查找合规依据。
    """
    ...
```

## 13. 非功能需求

### 13.1 性能需求

| 指标 | 要求 |
|------|------|
| API 响应时间（非 LLM 接口） | P95 < 500ms |
| 文档解析（50 页 PDF） | < 30 秒 |
| 知识库构建（100 条分块） | < 2 分钟（含 embedding） |
| 单次合规审查（端到端） | 2-5 分钟（取决于 LLM 响应速度） |
| RAG 问答响应 | 首 token < 3 秒（流式），完整 < 15 秒 |
| 并发用户 | 支持 50 并发用户 |
| 向量检索延迟 | < 100ms（10 万条分块规模） |

### 13.2 安全需求

- 所有 API 必须认证（JWT），除 `/auth/login` 外。
- 密码使用 bcrypt 哈希存储，不得明文。
- 基于角色的访问控制（RBAC），前端路由和后端接口双重校验。
- 文件上传校验：MIME 类型 + 扩展名 + 文件头三重校验，防止恶意文件。
- 上传文件存储在非 Web 可访问目录，通过鉴权接口下载。
- API 限流：登录接口 5 次/分钟/IP，通用接口 100 次/分钟/用户。
- 敏感配置（API Key、数据库密码）通过环境变量注入，不硬编码。
- LLM 调用日志中不得记录用户敏感信息（可选脱敏）。
- 支持 HTTPS（生产环境由反向代理终止）。

### 13.3 可用性需求

- 系统可用性 ≥ 99.5%。
- LLM 服务不可用时，RAG 问答和审查功能降级提示，不影响项目/文档/知识库管理功能。
- 向量库不可用时，知识库管理功能可用，检索功能降级。
- 异步任务失败后支持手动重试。
- 数据库定时备份（每日全量 + binlog 增量）。

### 13.4 可扩展性

- 向量库抽象层支持 PGVector ↔ Chroma 切换，无需改业务代码。
- Embedding 抽象层支持 OpenAI / 本地 BGE 切换。
- LLM 通过 OpenAI 兼容接口，支持 DeepSeek、Qwen、GPT 等切换。
- Agent 工作流通过 LangGraph 图定义，新增 Agent 只需加节点 + 边。
- 法规类别支持配置化扩展（七大类为基础，可通过配置新增子类）。

### 13.5 可观测性

- 结构化日志（loguru），按日期滚动，保留 30 天。
- 每次审查的 Agent 执行轨迹（输入、输出、耗时、token）存入 `reviews.agent_trace`，前端可查看。
- API 请求日志（方法、路径、状态码、耗时、用户 ID）。
- LLM 调用统计（token 消耗、调用次数、按日/按月），在系统设置页展示。
- 健康检查接口 `GET /health`（数据库、Redis、向量库、LLM 连通性）。

```nginx
server {
```

     `mcp/test_tools.py`（脱离 LLM 可测），再让 Agent 通过 MCP 取数。
     工具 docstring 必须写清「何时该用」，这是模型判断调用时机的依据。
14. **Token 预算不可省**（第 10.1 节）：`TokenBudget` 必须在第一个 Agent 执行前接入，
     超预算按序降级（减少召回 → 压缩上下文 → 模型降级 → 标记降级执行），
     **不得直接抛异常中断流程**。
15. **Trace 全程记录**（第 12.3 节）：每个 Agent 环节的输入摘要、输出摘要、耗时、
     token、工具调用、拒答次数必须写入 `reviews.agent_trace`，供前端可视化。
16. **成本数据必须真实**（第 12.2 节）：README 中的 token 消耗对比必须是实际跑出来的数据。
     **禁止填写预期值或估算值**——面试官会追问数据怎么来的。
17. **Bad Case 归因**（第 9.4 节）：评测失败项自动归类到六种失败类型，
     输出 `bad_cases.jsonl`，作为下一轮迭代的输入。
